- P5-03 interpretation choices and limits (review, `ReviewService`):
  - **Write order:** `set_review` (conditional on PENDING, which decides concurrent reviews) -> event (appended with `at = reviewed_at`) -> approve-only document pointer. Nothing is reverted after the event is written.
  - **Double failure (event append fails AND revert fails):** caller gets the original error, 500 `INTERNAL_ERROR`, no exception text. The revision stays APPROVED (`anchor.status=ANCHORING`) or REJECTED with `reviewed_by` set, has no event, and the pointer is unchanged. An ERROR log line gives the ids, and a retry gets 409 `REVISION_NOT_PENDING`. There is deliberately no "unknown state" marker: it would be one more write that could fail, and "reviewed with no event" can already be found by a query. The P5-04 reconciler Accept line covers it.
  - The same state is left, never reverted, when the append fails and the follow-up event lookup also fails, because the event may exist and an event pointing at a PENDING revision could not be repaired. An append that commits then raises is detected by the lookup and treated as success.
  - A pointer write that fails after the event is logged, and the request still returns 202. Repaired by the P5-04 reconciler (compare-and-set, 60 s grace).
  - **Maker != checker covers reject too** (04 only states it for approve); noted in 04. There is no ownership or team rule for approvers.

- P5-04 interpretation choices and limits (anchoring, `AnchorService` / `Reconciler`):
  - **Single-worker assumption (decided, no guard built).** The web3 nonce lock is per process, and a claim is only taken over once it is older than 10 minutes (`attempted_at`), which assumes one API worker. With several uvicorn workers or replicas, two processes could send txs with colliding nonces, and a reconciler on one worker could re-send a claim another worker is still processing only after 10 minutes. **Revisit at P10+ if multiple workers are ever introduced** (options: a leader-elected anchoring worker, or a Mongo lease plus a nonce manager).
  - **Anchor ordering:** revision N is not sent while an older APPROVED revision of the same document is not ANCHORED; it stays queued (`ANCHORING`, `attempted_at` null) and is sent when the predecessor anchors (successor drain in `AnchorService.anchor`). Approval itself is never blocked. A queued revision behind a FAILED predecessor waits for the admin retry of that predecessor (or the next startup reconcile).
  - **Retries:** 3 attempts (1 s, then 4 s) only for `ChainUnavailableError`; contract/node rejection and receipt timeouts go straight to FAILED. `anchor.attempts` counts claims, not chain calls.
  - **Reconciler runs once at startup only** (background task, off under APP_ENV=test unless `create_app(reconcile_on_startup=True)`); there is no periodic run. A FAILED revision is re-sent at every restart.
  - **FAILED with no ANCHOR_FAILED event is deliberately NOT repaired**: the next retry writes its own events.
  - **Pointer:** `latest_approved_version_no` is the on-chain version of the pointed-to revision, null while it is anchoring or FAILED (03 note). The reconciler also clears the pointer if a document has no APPROVED revision left (reachable since P5-05 revoke; `test_pointer_to_a_revoked_revision_is_cleared`).
  - Events written by anchoring have `actor_id: null` (system) and `data.trigger` = approve / retry / reconcile / successor; reconciler-appended events carry `data.reconciled: true` and use the repair time as `at`, so a repaired REVISION_APPROVED can sit after VERSION_ANCHORED in the chain.
  - Retry endpoint on a queued or in-flight anchor returns 409 `CONFLICT` (existing generic code); a stuck claim cannot be force-retried by an admin, only by the startup reconciler after 10 minutes.
  - Untested branches (coverage): document missing during anchoring, "claim lost" after the chain call or before recording a failure, a pointer-step exception inside the reconciler, and a startup-reconcile crash. All only log.

There is no per-document "status" field; if one is ever wanted (e.g. "current state"), it is a new filter, not a change to this one.
  - Revoke is **synchronous** (200) and requires `anchor.status == ANCHORED` (409 `CONFLICT` + `details.anchor_status` otherwise; not-APPROVED stays 409 `REVISION_NOT_APPROVED` + `details.status`). An APPROVED revision whose anchor FAILED cannot be revoked until it is anchored (retry-anchor first).
  - **Write order: chain -> revision (conditional on APPROVED + ANCHORED) -> VERSION_REVOKED event -> pointer.** Chain errors (503/502) write nothing. If the Mongo write fails after the chain revoke, chain and Mongo disagree (chain revoked, Mongo APPROVED) until the revoke is retried; the retry reads the chain, sends no second tx, and records `revocation.tx_hash = null` + event `already_revoked: true`. That window is NOT repaired automatically (the reconciler does not scan the chain); the P6 RECORD_MISMATCH follow-up (compare on-chain `revoked`) is what would detect it.
  - Event or pointer failure after the state write: 200 anyway, logged (class names and ids only); the reconciler appends VERSION_REVOKED and repairs the pointer (`test_reconciler_revoke.py`).
  - Concurrent revokes are serialized by one in-process `asyncio.Lock` (per event loop): one tx, one event, the loser gets 409. Same single-worker assumption as anchoring (see P5-04).
  - `reason`: required, max 500 chars, and **public** (written on-chain in `VersionRevoked`). Noted in 03/04; the API does not scan it for personal data.
  - Pointer after revoke: newest remaining APPROVED revision (its `version_no`, or null if it is still anchoring), or null/null. Re-submitting the same content after a revoke anchors a fresh version (`test_reanchoring_same_content_after_revoke_is_a_new_version`).
  - Reads: any authenticated user sees every document (04 "any"); there is no per-owner visibility. `GET /documents/{id}` takes the latest approved revision from the revisions, not from the pointer. `q` is regex-escaped. `/revisions/{id}/file` still has the "Presigned URL host" limit (Follow-ups, P8-03/P10-03).

- Chunking hard-split risk (found in P1-05): a sentence over 600 chars with no space is cut at exactly 600 code points (`_hard_split` in chunking.py, 02 §4 "hard split if no space"), which could separate a combining mark from its base character. NFKC (§3 step 1) composes most base+mark pairs into single code points, which minimizes this, but it is not ruled out for v1 (e.g. marks with no precomposed form). The split is deterministic, so hashes stay stable; the cost is a chunk boundary in an odd place. Avoiding it would change §4, needing an ADR in 09_DECISIONS.md and a `CANON_VERSION` bump. Do not change silently.

- Localization (P1-08, P9-03): page-boundary handling of a chunk that moves between pages (02 §9.3). One root cause, two symptoms, depending on which path runs: (a) when whole-document alignment runs (page counts differ, or spill-over detected), a moved chunk with unchanged text is matched as equal, so the verdict is CHANGED with zero regions for that move (§9 diffs chunk text only; pinned by `test_moved_chunk_without_text_change_has_no_regions`; listed in 02 §13); (b) when the spill-over test does not fire (it only looks at chunk-count changes, so inserts and deletes that leave the counts on neighbouring pages equal stay on the fast path, P1 review finding 6, pinned by `test_equal_count_swap_between_adjacent_pages_stays_on_fast_path`), per-page alignment sees the same move as DELETED + INSERTED. Observed in P9-03: `multi_edit-rerender-035` (5 edits, 8 pages, all page counts equal): the unedited chunk `20.1 If any provision is held invalid...` moved from page 4 (`p4-c0`) to page 3 (`p3-c22`), same text and leaf hash, reported as 1 DELETED + 1 INSERTED (2 false regions, chunk precision 0.992 for multi_edit, 1 of 300 cases; recall unaffected, verdict unaffected). Fixing either symptom needs an ADR (a page-move notion, or a spill-over rule based on leaf hashes instead of counts).
